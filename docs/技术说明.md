# 云屿园区数字孪生运营平台 · 技术说明

> 面向想了解「数字孪生大屏是怎么做出来的」的初学者。不讲通用前端知识，只讲数字孪生本身的技术原理：每节先说「它解决什么问题」，再说「本项目怎么做的」。撰写于 2026-11-01，对应代码 `package.json` v0.1.0、数据 `manifest.json` v1.2.0。

## 1. 一句话总览

数字孪生 = 把物理园区在数字空间里造一个**镜像**，再用数据驱动这面镜子「活」起来。本项目做三件事：用经纬度和高度把 128 栋楼「放」到虚拟地球上的正确位置（**定位**）；用三维渲染把它们画出来并能点、能看（**呈现**）；用模拟的告警、轨迹、实时推送让画面随时间变化（**驱动**）。全部技术栈（Vue 3 + Cesium + Pinia + ECharts + Leaflet）都只是这三件事的载体，本文只解释它们背后的原理。

## 2. 坐标系：楼是怎么「放对位置」的

**问题**：真实世界的楼在地球表面，电脑里的三维场景用的是 XYZ 直角坐标，两边怎么对上？

**做法**：所有数据用 WGS84 经纬度（全球通用的地理坐标，GPS 同款）。生成脚本先在「局部米制平面」上摆楼（以 `(120.4145, 36.0545)` 为原点，x、y 单位是米），再按 `经度 = 原点 + x/90000`、`纬度 = 原点 + y/111000` 换算成经纬度——90000 和 111000 就是该纬度下「1 度 ≈ 多少米」，这就是曲率换算的简化版。Cesium 拿到经纬度后，内部再换算成地心 XYZ 坐标。

**为什么楼是「拉伸」而不是「建模」**：精细建模（每栋楼一个 3D 模型文件）成本高、体积大。白模的做法是：只给楼的**底面轮廓 + 高度**，让引擎把平面多边形沿高度方向「拔」成立方体——Cesium 里就是一个 `extrudedHeight`（拉伸高度）参数。本项目 128 栋楼全部如此，所以叫「白模」：没有窗户纹理，只有体块和颜色，换来的是 396KB 数据量和毫秒级生成。

## 3. 三维场景是怎么画出来的

**问题**：显卡每画一样东西都要 CPU 下一次「绘制指令」（Draw Call）。东西多了，光下指令就把帧率拖垮。

**两种画法，各管一件事**：

- **Entity（实体）**：高级 API，一个对象一个实体，改颜色、改位置、绑定点击都方便。代价是每个实体都可能产生独立绘制。本项目的楼栋、设备点、告警点、路径、标签都用它——因为它们需要单独拾取和随时变化。
- **Primitive（图元）**：低级 API，把很多几何体**合批**成一个绘制单元。类比：寄 100 个小包裹，不如打包成 1 个大包裹——115 栋周边楼宇被合并成**单个** Primitive，一次 Draw Call 画完，这是全场 Draw Call 只有 93–99 的关键。代价是合批后不能单独点选、单独改色（业务上也不需要）。

**立体感从哪来**：白模只是纯色立方体，看着立体靠三件事——透视投影（近大远小）、深度测试（近的挡住远的）、相机俯角（同时看到屋顶和侧面）。模型矩阵负责把每个物体从「自己的坐标」变换到「世界坐标」，这是所有三维引擎的底层机制，本项目没有直接操作它（Cesium 内部完成），但合批 Primitive 正是靠共享一次变换来省开销。

## 4. 相机与拾取：眼睛和手指

**相机就是眼睛**。三级视角（片区 → 园区 → 楼栋）没有魔法，本质是三组参数化配置：看哪里（目标点/包围球）、离多远（距离）、什么角度（俯仰角）。例如园区总览 = 以园区中心为球心、距离 1700m、俯仰 -38°。

**飞行为什么用 flyTo 而不是直接改坐标**：瞬移会让人迷失空间关系。`flyToBoundingSphere` 在起点和终点之间自动插值出一条平滑轨迹，1.6–1.8 秒、缓入缓出，观众始终知道「我从哪飞来、飞到了哪」。新飞行会自动取消进行中的飞行，所以连续点击不会打架。

**拾取（pick）怎么知道点中了哪栋楼**：鼠标点击只给出一个屏幕像素坐标 `(x, y)`。Cesium 用「拾取帧」机制：把场景以特殊着色画到一块不可见画布，每个可拾取对象涂成不同颜色，读取鼠标位置那个像素的颜色，反查回对象 ID——相当于给每个物体发了一张「颜色名片」。本项目在此基础上做了两件事：因页面整体 CSS 缩放、默认坐标会偏，改为在 canvas 上自行换算坐标再 pick；拖拽超过 4px 视为「想转视角」而不触发选中。

## 5. 时间与动态：孪生为什么要「动」

静态模型只是沙盘，孪生的价值在于**随时间变化**。本项目有三条时间线：

- **模拟实时推送**：用 5 秒定时器假装有 WebSocket，交替推新告警和设备状态。「断线重连」演示的是真实系统的必备能力：断线 3 秒后自动重连并重发最后一条，业务层按消息 ID 去重——重发不会变成两条告警。
- **轨迹回放**：1200 个轨迹点每个都带时刻。拖动时间轴时，先算出「当前时刻」，再在每条轨迹的点列里**二分查找**该时刻的位置，移动标记用 `CallbackProperty`（每帧回调取位置的属性）——位置是「问出来的」，不是每帧重建几何，所以回放流畅。多条轨迹按各自开始时间错峰出现。
- **告警处置时间线**：「接警→确认→派发→到场→处理→归档」六阶段本质是状态机：每个阶段对应一组状态变更（改告警状态、写日志、触发路径规划），画面只是状态的投影。车辆行进动画按路径长度自适应 3.5–9 秒，抵达后自动把状态机推进到「到场」。

## 6. 视觉表达：Shader 与材质

**问题**：楼体变红、边界流光、地面扫描环这些效果，改颜色参数做不到，怎么办？

**原理**：屏幕每个像素的颜色由「片元着色器」逐像素算出。自定义 Shader 就是给显卡写一段小程序：输入像素位置和时间，输出颜色。本项目注册了两个材质（GLSL 代码）：

- **边界流光**：利用边界环线上每个像素的归一化位置 `st.s`（0→1 绕园区一圈），让它和一个随帧数循环前进的「光带头部」比较距离，越近越亮——看起来像光沿边界流动；
- **地面扫描环**：算每个像素到园区中心的距离，和一个随时间扩散的「相位」比较，重合处发光——像雷达扫描。

两者都靠 GPU 内置帧号自驱动，**不需要 CPU 每帧传参数**。告警热力用两个不同大小/透明度的椭圆叠加模拟光斑（成本更低的近似）。这些效果加上「红色半透明体 + 脉冲扩散圆 + 高亮描边」，就是告警楼体能从 128 栋楼里「跳出来」的原因。

## 7. 性能：数字孪生的命门

**问题**：三维大屏一卡，所有演示都垮。帧率（FPS）由每帧的 Draw Call、三角形数量、像素填充量共同决定。

**本项目的做法**：合批（§3）降 Draw Call；`resolutionScale`（渲染分辨率缩放）降填充压力——画质三档：高清 1.0 + 4 倍抗锯齿、均衡 0.9、省电 0.75 并直接关掉周边楼宇图层；大屏适配时用 `min(2, 档位基准 × 屏幕缩放比)` 反向提高分辨率，4K 下不发糊。一个已知取舍：未启用 `requestRenderMode`（静止时不渲染的模式），因为轨迹和告警脉冲本来就需要连续渲染。

**实测**（引自《数据说明》本机 1080p 记录，本文未复测）：FPS 60 稳定、Draw Call 93–99、图元约 420–440。含义很简单：每秒能画 60 帧、每帧不到 100 条绘制指令，属于「流畅有余量」的水平。性能面板里的 FPS/Draw Call/内存就来自渲染循环的真实统计，不是估算。

## 8. 道路寻路：地图变成图

**问题**：「消防车怎么去 3 号楼」不能只画直线——车要沿路走。

**原理**：把路网抽象成数学上的「图」：道路交点/端点是**节点**，相邻节点间的路段是**边**，边长是**权重**。本项目建图时把坐标保留 4 位小数（约 9–11m 网格）做「吸附」，让本不相交但离得近的道路也能连通。寻路用 Dijkstra 算法：从起点开始，像水波一样一圈圈向外扩展，每到一个节点就记下「到这的最短距离」，直到抵达终点——保证找到最短路径。节点只有几百个，用最简单的数组扫描就够了。

**路径变动画**：Dijkstra 输出一串经纬度拐点，预先算出相邻点距离和累计总长，动画每帧按「已走比例 × 总长」在路径上线性插值出当前位置，车辆点就沿路飞起来了；起终点先吸附到最近道路节点再替换回精确位置，保证路径贴路且精确到门口。

## 9. 技术债与可改进方向

- 自定义材质、性能统计用了 Cesium 内部 API（`_materialCache`、`frameState.commandList`），升级引擎需回归验证；内存指标仅 Chromium 有效。
- 省电档强制关闭周边楼宇图层且切回不自动恢复；840 行单 store 宜按域拆分；无自动化测试（靠 vue-tsc + 生成脚本断言）；场景「Step 3」徽标与趋势图 09–14 点六档为硬编码。
- 可扩展：`public/tiles|models/` 已预留，可换 3DTiles/glTF 精细模型；实时链路是接口化回调，可换真 WebSocket；热力可升级为真后处理方案。
